### 5. 安装验证（已完成·一键脚本）

所有工具装完后，逐项跑命令确认可用。**纯本地验证不需要网络/代理**；标注「需代理」才需要开 Clash Verge。

```bash
echo "=== 工具装好 + 架构确认 ==="
for t in kubectl helm terraform git docker; do
  if command -v $t >/dev/null 2>&1; then
    case $t in
      kubectl) v=$(kubectl version --client 2>&1 | head -1) ;;
      helm)    v=$(helm version 2>&1 | head -1) ;;
      *)       v=$($t --version 2>&1 | head -1) ;;
    esac
    a=$(file $(command -v $t) 2>/dev/null | grep -oE "arm64|x86_64|universal" | head -1)
    printf "%-10s [OK] %-28s arch=%s\n" "$t" "$v" "$a"
  else
    printf "%-10s [MISSING]\n" "$t"
  fi
done
printf "%-10s " "code"; command -v code >/dev/null 2>&1 && code --version 2>&1 | head -1 || echo "[需装 Shell Command]"
echo "=== 纯本地功能验证（无需网络/集群）==="
helm create /tmp/tc >/dev/null 2>&1 && helm lint /tmp/tc 2>&1 | tail -1; rm -rf /tmp/tc
mkdir -p /tmp/tfv && printf "terraform {\n  required_version = \">= 1.0\"\n}\n" > /tmp/tfv/main.tf
(cd /tmp/tfv && terraform init >/dev/null 2>&1 && terraform validate 2>&1 | tail -1)
echo "=== Git 身份 ==="
printf "user.name : %s\n" "$(git config --global user.name || echo 未配置)"
printf "user.email: %s\n" "$(git config --global user.email || echo 未配置)"
```

### 6. Docker 镜像加速器配置（必做，否则拉镜像超慢）

Docker Hub 在国外，国内直连 `docker pull` 极慢且易超时。

**方案 A（推荐·国内直连·免代理）：配置 registry-mirrors**

> ⚠️ **先澄清误区（来自 2026-10-18 真实踩坑）**：
> - **ACR 个人版 ≠ 镜像加速器**。它是私有仓库，用来**存你自建镜像**（Day1 推送目标），**不会**代理你拉取 Docker Hub 上的 nginx/redis 等公共镜像。
> - 阿里云有一条**「镜像加速器」**功能（独立于 ACR 仓库），提供**专属加速地址** `https://<你的ACR实例ID>.mirror.aliyuncs.com`，可加速 Docker Hub 公共镜像拉取。需在 ACR 控制台「镜像加速器」页领取专属地址并配入 daemon.json 才生效。
> - 阿里云**公共端** `mirror.aliyuncs.com`（不绑定实例那种）2026 年已停用，**别用**。

**按场景选源（关键区分）**：
- **在阿里云 ECS 上（云内网）** → **首选阿里云专属镜像加速器**：ECS 与 ACR 同地域时走**内网直连**，最快最稳、且 ECS↔ACR 内网流量**免费**（公网出流量才收费）。这是 ECS 上的最优解（用户 2026-10-18 提醒确认）。
- **在本地 Mac 上（家宽公网）** → 到 aliyuncs.com 走公网、内网优势发挥不出，优先用实测存活的第三方公共源（轩辕/DaoCloud/南大）更快；也可领阿里云专属地址公网用，但不如 ECS 上香。
- **地域对齐**：ECS 与 ACR 镜像加速器务必选同一地域（你都在**华东1 杭州**），才能走内网；跨地域会退化为公网、变慢且计费。

- ✅ **阿里云专属加速地址（ECS 云上首选·需领）**：登录 aliyun.com → 容器镜像服务 ACR → 镜像加速器 → 复制专属地址（形如 `https://xxxx.mirror.aliyuncs.com`），配入 daemon.json 首位
- ✅ **免费且实测存活的公共加速器（2026-10 本地探测 401 存活）**：轩辕 `https://docker.xuanyuan.me`、DaoCloud `https://docker.m.daocloud.io`、南京大学 `https://docker.nju.edu.cn`（nju 探测 403，基本可用）
- ❌ **已确认死亡（探测 000，勿用）**：上海交大 `docker.mirrors.sjtug.sjtu.edu.cn`、中科大 `docker.mirrors.ustc.edu.cn`、网易 `hub-mirror.c.163.com`、腾讯云 `mirror.ccs.tencentyun.com`（**本机 2026-10-18 正是配了交大+中科大导致 pull 全报错**）
- 配置示例（阿里云专属地址首位 + 第三方 failover）：Docker Desktop(Mac) → Settings → **Docker Engine** 编辑 JSON；ECS 写 `/etc/docker/daemon.json`：
  ```json
  {
    "registry-mirrors": [
      "https://<你的ACR实例ID>.mirror.aliyuncs.com",
      "https://docker.xuanyuan.me",
      "https://docker.m.daocloud.io",
      "https://docker.nju.edu.cn"
    ]
  }
  ```
  Mac 点 Apply & Restart；ECS `systemctl daemon-reload && systemctl restart docker`。验证：`docker info` 末尾应出现 `Registry Mirrors:` 列表且首项为你的 aliyuncs 地址。

**方案 B（备选·需 Clash 节点通）：Docker daemon 走代理**
- Docker Desktop → Settings → **Resources → Proxies** → 勾选 Manual proxy → HTTP/HTTPS 均填 `http://127.0.0.1:7897`（Clash Mixed Port）

> 注意：`docker search` 直连 Docker Hub 索引会被墙（坑 14），查询镜像改用 `hub.docker.com` 网页；`pull` 走上面加速器即可。

## 第 0 天（续）：本地环境搭建踩坑记录（SOP 素材）

> 本节点记录 Day 0 实际踩过的坑与确凿解法，供后续上传 Git 仓库沉淀为《Mac M1 DevOps 环境搭建 SOP》。每条按「现象 / 根因 / 解法 / 防复发」组织。

### 坑 1：Terraform `brew install` 报 "No available formula"
- **现象**：`brew install terraform` → `No available formula with the name "terraform"`
- **根因**：Homebrew core 已移除 Terraform
- **解法**：`brew tap hashicorp/tap && brew install hashicorp/tap/terraform`
- **防复发**：Mac 装 TF 一律走 hashicorp/tap；别在 brew 列表里乱选 terraformer / terraform-ls 等相似包

### 坑 2：国内镜像站下载 HashiCorp 二进制是"假包"
- **现象**：`curl` 华为云 mirrors hashicorp 的 zip → `unzip` 报 `End-of-central-directory signature not found`
- **根因**：华为云该镜像是任意路径返回 `200 + 首页 HTML` 的 SPA 陷阱（实测 12KB HTML，非 zip）；中科大/腾讯/阿里/清华同类镜像均 404
- **解法**：唯一确凿可下真包的是官方 `releases.hashicorp.com`（25.7MB 真 zip），但国内直连需代理
- **防复发**：HashiCorp 二进制别指望国内镜像 curl；正道是终端走通 Clash 代理后 `brew tap hashicorp/tap` 安装

### 坑 3：终端 `brew tap` 连 GitHub 失败
- **现象**：`brew tap hashicorp/tap` → `fatal: unable to access github.com`
- **根因**：Clash **系统代理只影响 GUI 应用**，终端默认不走；开关 Clash 没用
- **解法**：终端手动注入 `export https_proxy=http://127.0.0.1:7897`（Clash Mixed Port，默认 7897）；或开 Clash TUN 模式让全局走代理。国内源操作前 `unset https_proxy` 直连
- **防复发**：凡 `brew tap` / 访问境外源，先 `export https_proxy`；国内源先 `unproxy`

### 坑 4：kubectl / helm 版本探测 "unknown flag: --version"
- **现象**：验证脚本里 `$t --version` 对 kubectl/helm 报 `unknown flag: --version`
- **根因**：新版 kubectl/helm 已不支持 `--version` 这个 flag
- **解法**：kubectl 用 `kubectl version --client`；helm 用 `helm version`
- **防复发**：§5 一键脚本已修；自写探测时别对这两个用 `--version`

### 坑 5：Git 全局身份未配置
- **现象**：`git config --global user.name` 为空，首次提交报错
- **解法**：`git config --global user.name "linux321"` / `git config --global user.email "deng1335770891@gmail.com"`（按实际改）
- **防复发**：新机第一步先配 Git 身份

### 坑 6：`code` 命令 not found
- **现象**：终端 `code` → command not found
- **根因**：VS Code 的 `code` 命令需手动安装到 PATH，不是扩展商店里的插件（别去搜插件）
- **解法**：VS Code 内 `Cmd+Shift+P` → 搜 `Shell Command: Install 'code' command in PATH` → 执行后重开终端
- **防复发**：装完 VS Code 第一件事就是装这个 Shell Command

### 坑 7：Docker Desktop 客户端本体下载极慢
- **现象**：docker.com 下 .dmg 卡死
- **根因**：Docker Desktop 闭源客户端，国内镜像站不提供，只能官网+代理
- **解法**：① 开 Clash 系统代理（GUI 走系统代理）+ 浏览器开 docker.com 下；② 或 DaoCloud 国内下载站 `https://get.daocloud.io/`
- **防复发**：客户端本体只能官网 / DaoCloud，别找"国内镜像"

### 坑 8：Docker 镜像加速器 2026 可用源
- **现象**：照旧教程配中科大/网易/七牛/阿里云公共端加速器 → pull 仍慢或失败
- **根因**：这些旧源 2026 年已失效或间歇性
- **解法**：用 2026-09 实测可用源做 failover：轩辕 `https://docker.xuanyuan.me`、DaoCloud `https://docker.m.daocloud.io`、南京大学 `https://docker.nju.edu.cn`；最稳是阿里云 ACR 专属加速地址
- **防复发**：§6 已固化清单；新机直接抄 §6 JSON

### 坑 9：Mac 上多个 Python 版本，误删依赖
- **现象**：`brew uses` 显示 `python@3.13` 被 `openjdk@17` 依赖、`python@3.14` 被 `openai-whisper` 依赖
- **根因**：openjdk@17、openai-whisper 各自带 Python 依赖，不能盲目 `brew uninstall python@x`
- **解法**：保留不动；项目用哪个版本显式指定即可
- **防复发**：卸载 Python 前先 `brew uses --installed python@x` 确认无依赖

### 坑 10：系统 git 优先于 brew git（arch 显示 x86_64）
- **现象**：`which git` → `/usr/bin/git`，验证里 arch=x86_64
- **根因**：系统自带 universal git 在 PATH 前，brew git 没覆盖
- **影响**：不影响使用（universal 含 arm64）
- **解法（可选）**：`brew link git --force` 让 brew 版优先；或调 PATH
- **防复发**：arm64 验证里 git 显示 x86_64 / universal 均正常，不必强求

### 坑 11：ACK 无"免费试用"入口，ASK 免费额度也不可领
- **现象**：控制台找不到 ACK 免费试用按钮；ASK 免费额度领取失败
- **根因**：托管版 ACK 只有"开通服务"免费、节点计费；无"免费试用"入口；免费额度对新用户/认证条件受限
- **决策**：**混合方案**——本地 kind/minikube 零成本日常练手 + 付费 ACK 托管版做真集群演示（练完释放节点/删集群控费）；或 ASK 按 pod 秒级计费
- **防复发**：别在控制台找"免费试用"；付费 ACK 练完务必释放，防空转扣费

### 坑 12：git clone GitHub 超时（RPC failed; curl 28）
- **现象**：`git clone https://github.com/...` → `error: RPC failed; curl 28 Failed to connect to github.com port 443 after 75015 ms` / `fatal: expected 'packfile'`
- **根因**：GitHub 在境外，终端/git 默认不走 Clash 系统代理（系统代理只管 GUI）；直连被墙导致 443 连不上、75s 超时
- **解法**：给 git 配代理（Clash Mixed Port 默认 7897）+ 浅克隆提速：
  ```bash
  git config --global http.proxy http://127.0.0.1:7897
  git config --global https.proxy http://127.0.0.1:7897
  git config --global http.postBuffer 524288000
  rm -rf /Users/dengzz/Documents/devops-journey-hangzhou   # 清掉上一次失败的空壳
  git clone --depth 1 https://github.com/linux321dark/devops-journey-hangzhou.git /Users/dengzz/Documents/devops-journey-hangzhou
  ```
- **防复发**：凡 `git` 操作 github.com 等境外源，先确认 git 代理已配；国内源（gitee/coding）则 `git config --global --unset http.proxy` / `https.proxy` 直连。端口以 Clash Verge → 设置 → 端口（Mixed Port）为准

### 坑 13：GitLab / 极狐(jihulab) push 要求 Personal Access Token（密码认证已禁用）
- **现象**：`git push` 弹用户名/密码，输登录密码后报 `remote: HTTP Basic: Access denied` / `fatal: Authentication failed`
- **根因**：GitLab 系（含 jihulab.com）已禁用 Git over HTTPS 的账号密码认证，必须用 Personal Access Token 当密码
- **解法**：jihulab → 个人设置 → Access Tokens → 建令牌（勾 `write_repository` 范围）→ push 时用户名填 `linux321`、密码填**令牌**（非登录密码）
- **防复发**：国内 GitLab 类仓库 push 一律用 PAT；或改 SSH 免密（本地 `ssh-keygen` + 公钥贴 jihulab SSH Keys）

### 坑 14：`docker search` 报 `context deadline exceeded`（Docker Hub 索引不可达）
- **现象**：`docker search nginx` → `Get "https://index.docker.io/v1/search?q=nginx": context deadline exceeded`
- **根因**：`docker search` 直连 Docker Hub 索引 API（`index.docker.io`），国内直连常被墙/超时；**registry-mirrors 只加速 `pull`，不覆盖 `search`**
- **解法**：①（推荐）不依赖 search：浏览器开 `hub.docker.com` 查镜像/标签，再 `docker pull nginx:1.27-alpine` 直接拉（pull 走国内镜像，快）；②（想用 search）让 daemon 走代理：Docker Desktop → Settings → Resources → Proxies → 手动代理 HTTP/HTTPS = `http://127.0.0.1:7897` → Apply & Restart；或开 Clash TUN 模式
- **防复发**：Day 1 学习阶段根本不需要 search；下午 `docker pull` 能否成功取决于 §6 镜像加速器是否配好（验证 `docker info | grep -A3 "Registry Mirrors"` 非空），search 失败不影响 pull

### 坑 15：阿里云 ACK/ACS 按量付费要求「账户余额+代金券 ≥ 100 元」门槛（未提前告知导致开不了实例）
- **现象**：在 ACK / ACS 控制台创建按量付费集群时提示无法创建，或文档写明"账户余额需 ≥ 100 元"——账户没钱/钱不够就开不了任何按量实例（含 ACK 托管版、ACS、ASK、ECS、RDS 等）。
- **根因**：阿里云官方规则（配额文档 `help.aliyun.com/document_detail/86741.html`[ACK]、`help.aliyun.com/document_detail/2584485.html`[ACS] 明确，2026 仍执行）：创建按量付费资源前，账户余额与代金券总值必须 ≥ 100 元。**这是「可用额度门槛」而非消费额**——100 元充进账户不被扣掉，按量资源按小时（约 ¥0.5–1/小时）从中扣，不花不动。
- **解法**：① 想用真集群，提前往账户充值 100 元现金（或凑足 ≥100 元代金券）；② 不充值也能学——全程用本地 `kind`/`minikube` 跑 K8s（零成本、零门槛、Day 1–14 全覆盖），付费真集群仅作 Day 15 演示素材、可要可不要。
- **防复发**：凡涉及阿里云按量付费，先把"余额≥100元门槛"写进预算前置条件；且区分"门槛（可留存抵扣）"与"实际花费"，不混淆。**代金券慎用凑门槛**：多数代金券限定"包年包月新购/续费"场景、不支持 ACK/ACS 按量付费账单抵扣（且工行企业账号下的代金券属工行资源、严禁用于个人求职项目）；即使算进100元"总值"门槛，真扣费仍走现金账户、代金券用不上，反而白忙。最干净：直接充100元现金到现金账户，或干脆走本地 kind 零成本不充。
- **关键澄清（2026-10-18 用户问）**：100 元是**创建资源的开户门槛（一次性校验）**，**不是运行期维持门槛**。创建成功后只需"可用额度≥0"（=现金余额+信控额度−未结清账单）资源即正常运行；扣到 99/50/30 元都正常，**低于 100 无需补充**。仅当余额扣到**负数（可用额度<0=欠费）**才触发 15 天停机保留期（停机、停计费、数据保留），15 天内补足即恢复、超 15 天释放。对 ACK 学习用法（创建→用一阵→释放/缩容到0）而言，100 元撑 2vCPU/4G 节点约 100–200 小时，全程基本不触欠费线，**无需反复充值**；唯一真风险是"忘记释放集群导致空转扣费"，靠费用警报+用完即删规避。

### 16. 云 ECS 使用纪律（防超时 / 防被扫 / 防烧钱 / 防架构坑）
- **背景**：2026-10-18 用户充值 100 元跨过按量门槛，购买**独立 ECS 云服务器**（非 ACK 集群节点）并自装 Docker 29.9.1，作 Docker/K8s 练习机。ECS 是裸机、完全可控、最接近生产，比本地 kind 更适合后期真部署验证。
- **必做 1 · 配 registry-mirrors（否则 pull 必超时）**：云实例是干净系统，默认直连 Docker Hub 国内超时（同 Mac 坑）。装好 Docker 第一件事就是写 `/etc/docker/daemon.json` 配国内源，**ECS 上首选阿里云专属镜像加速器（内网直连最快最稳、内网免费）**：登录 ACR 控制台 → 镜像加速器 → 复制专属地址（形如 `https://<实例ID>.mirror.aliyuncs.com`）放列表首位，再叠加第三方 failover（轩辕 `docker.xuanyuan.me` / DaoCloud `docker.m.daocloud.io` / 南京大学 `docker.nju.edu.cn`，2026 实测存活；**交大/中科大已死勿用**）。daemon.json 示例与场景区分见 §6。配完 `systemctl daemon-reload && systemctl restart docker` 后 `docker pull alpine:3.21` 验证。
- **必做 2 · 安全组收口（防被扫）**：ECS 默认安全组可能全开。务必：① 仅放行 22（SSH），源限你本机 IP（或临时 0.0.0.0/0）；② **绝对禁止**把 Docker 守护端口 2375/2376 对公网开放（等于送 root）；③ 后续跑 K8s 再按需开 6443（apiserver）、30000–32767（NodePort），不开全端口。
- **必做 3 · 用完释放/停机（防烧钱）**：练习完 `stop` 或 `release` 实例；按量 ECS 停机后**仍可能计系统盘/公网 IP 费**，彻底不用就释放。设费用警报（余额<20 短信）。
- **关键坑 · Mac arm64 ≠ ECS amd64（架构差）**：Mac 是 `arm64`、ECS 多为 `x86_64/amd64`。在 Mac 上 `docker build` 出的镜像是 arm64，**直接 `docker pull` 到 ECS 运行会因架构不匹配报错（exec format error）**。解法：① 用 `docker buildx build --platform linux/amd64 ...` 指定目标架构；② 或干脆在 ECS 上直接 build（最省心）；③ 推 ACR 时用 `buildx build --platform linux/amd64,linux/arm64` 打多架构镜像。这是 Mac 用户上云第一课。
- **关键认知 · containerd ≠ docker（K8s 阶段用）**：现代 K8s（1.24+）运行时是 **containerd**，不是 Docker。在 ECS 上跑 K8s（kubeadm 自搭或后续 ACK）时，你用 `kubectl` 操作，**不是 `docker` 命令**；`docker` 只管单机容器。面试常考，先建立区分。
- **定位 · Day 1 基础留本地、云上留后面**：Docker 多阶段构建基础练习在本地 Mac 做（免费快）；ECS 留给 Day 2+ K8s 部署、Day 15 真集群演示。别在云上烧钱练 Day 1 基础——但可用 ECS 做"同镜像在真 Linux 上跑通"的架构验证（注意上面的 amd64 坑）。

### 17. 版本号「先查仓库再钉死」铁律（2026-10-18 用户纠正）
- **现象**：文档/命令里写了具体版本号（Docker 基础镜像、apt 包、语言二进制、依赖版本），结果与实际环境对不上——Go 误写 `1.23.4`（实际 ECS 装的是 **1.26**），Ruby 文档钉 `ruby:3.3.6-slim` 而主机走 apt 装「最新不指定小版本」，导致主机/镜像版本不一致、构建期指令被拒（`go.mod requires go >= 1.26` / `bundle install` 的 `RUBY VERSION` 不匹配）。
- **根因**：版本号是**假设**，不是事实。拍脑袋写死 = 把假设当事实落文档，必然撞墙。
- **解法（通用）**：凡要装/钉「指定版本」，动手前先用对应仓库核验该版本真实存在：
  - Docker 镜像：`docker pull <img>:<tag>` 试拉（不存在立刻 `not found`）；或 `skopeo`/`crane ls` / Docker Hub API / 阿里云镜加端点 `curl .../v2/library/<img>/tags/list`。
  - apt：`apt-cache policy <包>` / `apt list -a <包>` 看全部可用版本。
  - 阿里云 Go / npmmirror Node 二进制：`curl -sI <下载URL>` 看 200/404。
  - 语言包：npm `npm view <包> versions`、pip `pip index versions <包>`、gem `gem search -r <gem>`、cargo `cargo search`、Maven 查 search.maven.org。
  - 完整命令表见 `day1-evening-practice.md` §0.6。
- **铁律**：① 钉版本保可复现**是对的**，但前提是版本真实存在；② **主机生成 lockfile 用的版本必须与 Docker 镜像基础版本对齐**（Go 已对齐 1.26.0；Ruby 须 `ruby -v` 查主机实际版后把镜像钉一致）；③ 凡涉及版本号，先问/查实际环境，不得拍脑袋写死。

### 18. Docker 29.x 推阿里云 ACR 报 `unknown manifest class ... oci.empty`（2026-10-18 实战踩坑）
- **现象**：ECS 上 `docker build .` 后 `docker push` 到 ACR 个人版，报 `error from registry: unknown manifest class for application/vnd.oci.empty.v1+json`，四层都 Pushed 后最后一步失败。
- **根因**：Docker 29 默认给镜像附 **provenance（构建来源/SLSA）产物**——推送时会多塞一个 `application/vnd.oci.empty.v1+json`（空 manifest）。**阿里云 ACR 个人版不认这个 manifest class**，直接拒收。与镜加无关、与镜像内容无关、与网络无关。
- **解法（正解）**：**不要用经典 `docker build` + `docker push` 两步**，改用 `docker buildx build` 构建并直接推送，并关闭 provenance/sbom：
  ```bash
  docker buildx build --provenance=false --sbom=false \
    -t registry.cn-hangzhou.aliyuncs.com/<ns>/<repo>:<tag> --push .
  ```
  一劳永逸：在 ECS `~/.bashrc` 加 `export BUILDX_PROVENANCE=false`，之后 buildx 构建不再附空 manifest。
- **铁律**：① ECS 装的是较新 Docker（29.x），**任何推 ACR 的动作一律走 `docker buildx build --push` 形式**，经典两步推必踩此坑；② 该错误只发生在「push 到 ACR」时，本地 `docker build`/`docker run` 不受影响；③ ACR 企业版/其他 registry 兼容性可能不同，但个人版目前确认拒收 oci.empty。

### 19. 镜像源/包源也要「先验证可用性」——`gems.ruby-china.com` 证书已不可靠（2026-10-18 实战踩坑）
- **现象**：按文档 §0.5 配 `gem sources --add https://gems.ruby-china.com/` + `bundle config mirror...ruby-china.com`，执行即报 `SSL_connect ... certificate verify failed (hostname mismatch)`，`bundle install` 直接死。
- **根因**：`gems.ruby-china.com` 这个域名 2026 起 **SSL 证书域名不匹配**（握手阶段 hostname mismatch），源本身已不可靠——这是「把没验证过的源写进文档」的代价，正是 坑17「先查仓库/源有没有、能不能用」的延伸。
- **解法**：换阿里云官方 RubyGems 镜像（证书可靠、同 ECS 阿里云内网最快，与全套 aliyun 源一致）：
  ```bash
  gem sources --add https://mirrors.aliyun.com/rubygems/ --remove https://rubygems.org/
  bundle config mirror.https://rubygems.org https://mirrors.aliyun.com/rubygems/
  ```
  Dockerfile 内 `RUN bundle config set --global mirror.https://rubygems.org https://mirrors.aliyun.com/rubygems/`。
- **铁律**：① 凡写进实操文档的「镜像源/包管理器源」，须先验证**当前仍可用**（证书有效、域名解析正常），不能照搬旧教程里的 `ruby-china`/`taobao` 等已劣化源；② 同体系优先用同一家（本环境=阿里云全家桶：Docker 镜加 + Go/Node/pip/Maven/Composer/RubyGems 全走 aliyun）；③ `gem sources` 若报 `Invalid source URI`，多半是 URL 末尾多了 `/`，去掉重试。

### 20. 基础镜像工具链别钉太旧——Rust 会被 MSRV / edition 反复卡死（2026-10-18 实战踩坑，已三次修正）
- **现象**：`docker build ./rust-demo` 在 `RUN cargo build --release` 先报 `feature edition2024 is required ... not stabilized (Cargo 1.83.0)`；升到 `rust:1.87.0-alpine` 又报 `rustc 1.87.0 is not supported by the following packages`（依赖 MSRV ≥1.88+）；再改 `rust:1-alpine` 浮动 tag 反而报 `feature edition2021 is required ... does not support nightly features`（cargo<1.56 才有的远古错）——**钉旧补丁被 MSRV 卡、用浮动 tag 又被镜加缓存成远古版**，两头堵。
- **根因**：① 钉死过旧具体补丁（1.83 / 1.87）永远慢于上游依赖 MSRV 门槛；② **本环境（阿里云镜加）对浮动 tag 会缓存陈旧 digest**——`rust:1-alpine` 被镜加返回了 cargo<1.56 的远古层，所以 edition2021 都要 nightly。两类错误都**与镜像源/网络无关**，纯工具链版本问题。
- **解法（三次修正·定稿）**：Rust 基础镜像**钉具体且当前较新的版本** `rust:1.99.1-alpine`（2026-10-13 稳定版；查最新：<https://static.rust-lang.org/dist/channel-rust-stable.toml>）。钉具体版本由镜加按 digest 现拉新层、避开了浮动 tag 的陈旧缓存，又远超依赖 MSRV。
- **铁律**：① 本环境（阿里云镜加）**不要用 Docker 浮动 tag**（`rust:1` / `node:22` / `golang:1` 等都可能被镜加缓存成旧 digest 而 `not found`/远古版）——**一律钉具体补丁版本**，并保持其较新；② 钉具体补丁≠越旧越稳，语言工具链类要留足余量（Rust 钉当前稳定版、Go 已对齐主机 1.26.0、Node 钉 22.x 较新补丁）；稳定慢变系统镜像（debian/nginx/ruby 已对齐主机）才适合长期钉老补丁；③ 凡遇 `feature X is required` / `rustc X.Y is not supported` / `edition2021 需 nightly`，先升工具链到当前稳定版，不要盲目 `cargo update` 降级依赖。

### 21. PHP 多阶段构建 composer install 报「require-dev is ignored」阻塞（2026-10-18 实战踩坑）
- **现象**：`docker build ./php-demo` 在 `RUN composer install --no-dev` 报 `Running update with --no-dev does not mean require-dev is ignored ... If dev requirements are blocking the update you have to resolve those problems`，exit 2 失败。
- **根因**：`composer install` 在**镜像内没有 `composer.lock`** 时会**退化为 update 模式**；Composer 2 在 `--no-dev` 下仍会**校验 `require-dev` 约束**，一旦 composer.json 带了 `require-dev`（或锁文件缺失/与 json 不一致）就阻塞退出。文档给的 composer.json 是干净的（仅 slim/slim + slim/psr7），所以**实际是 php-demo 目录里的 composer.json 被主机侧加了 require-dev**（如 `composer require --dev phpunit/phpunit` 残留），或目录里残留旧 lock 含 dev。
- **解法**：① **composer.json 切勿含 `require-dev`**（生产镜像不需要 dev 依赖，带了 `--no-dev` 仍会 dev blocking）；② 构建前在主机侧用同个阿里云源 `composer install` 生成 `composer.lock`，Dockerfile 里 `COPY composer.json composer.lock ./` 再 `composer install`（基于 lock，不退化 update）；③ 无 lock 时 Dockerfile 改用 `composer update --no-dev`（明确语义，仍要求 json 无 require-dev）；④ 加 `--ignore-platform-reqs` 兜底 alpine 上的 php 平台/扩展约束。
- **铁律**：PHP 多阶段构建 = **先主机生成 lock + Dockerfile COPY lock + install**，且 **composer.json 零 require-dev**；阿里云 composer 镜像（`mirrors.aliyun.com/composer/`，末尾 `/` 不能省）2026 仍可用，但**不要写死进 composer.json 的 repositories 字段**（优先级高于全局、易踩旧地址），用全局 `composer config -g` 即可。
